# part4-toeic-trainer

TOEIC Part 4（1人が話す説明文 + 設問3問）の練習セットを作る。**1回の実行で5セット**。

時事ネタではないので毎日作る必要がない。週に1回まとめて5セット作り、1日1セットずつ解く想定。
1セットは通勤の片道1回で終わる量。

出力先は学習アプリのリポジトリ `data/part4/`。アプリ（GitHub Pages 上の `part4.html`）はこの JSON だけを読む。

**本番の形式をそのまま再現することが唯一の目的**である。面白い話や凝った設問を作ることではない。本番で起きないことは、ここでも起こしてはならない。

**Part 3 との違い**は3つ。話し手が1人であること、冒頭に「何を聞くか」を告げる前置き（`intro`）が付くこと、設問の1問目がほぼ必ず「何の話か・誰の話か」であること。会話ではないので、聞き分けではなく**話の展開を追う力**を試す。

## ステップ0：日付・時刻の確定（必ず最初に実行）

日付・時刻の基準は必ず **JST（日本標準時, UTC+9）** とする。

1. 最初に必ずシェルで現在時刻を取得する。**`TZ=Asia/Tokyo date` を単独で信用しない。**
   タイムゾーン情報を持たない環境では `TZ` が黙って無視され、**UTC がそのまま返る**。
   9時間ずれた時刻で id を作ると、その日の分が前日扱いになる。

   ```bash
   node -e "console.log(new Intl.DateTimeFormat('sv-SE',{timeZone:'Asia/Tokyo',dateStyle:'short',timeStyle:'short'}).format(new Date()))"
   ```

2. `id` はこの実時刻から `YYYY-MM-DD-HHMM-N` として作る。`N` は**この回の何本目か**（1〜5）。
   例：`2026-09-20-0500-1` 〜 `2026-09-20-0500-5`。
   5本を同じ時刻で作るので、連番を付けないと id がぶつかってファイルを上書きしてしまう。
3. 実行環境が返すキャッシュ時刻（「as of ...Z」など）を現在時刻として使ってはならない。

## ステップ1：トークの種類と場面の決定

### 種類は3層の「重み付けローテーション」で選ぶ

`talkType` は次の9種から選ぶ。`intro` の言い回しは種類ごとに決まっており、**勝手に変えてはならない**。

**優先枠（高頻度・本番で最も出る）**

| talkType | intro の言い回し | 中身の例 |
|---|---|---|
| `voicemail` | the following telephone message | 業者からの折り返し、予約の変更、納期の連絡、面接日程 |
| `announcement` | the following announcement | 空港・駅・店舗・社内の館内放送、設備の停止、営業時間の変更 |
| `meeting` | the following excerpt from a meeting | 制度の変更、進捗の共有、方針の説明 |

**標準枠**

| talkType | intro の言い回し | 中身の例 |
|---|---|---|
| `speech` | the following speech | 表彰、歓迎、送別、開会の挨拶 |
| `ad` | the following advertisement | 店舗・サービス・求人の宣伝 |
| `broadcast` | the following broadcast | 交通情報、天気、地域や企業のニュース |

**低頻度枠**

| talkType | intro の言い回し | 中身の例 |
|---|---|---|
| `tour` | the following tour information | 工場見学、施設案内、社屋のツアー |
| `instructions` | the following instructions | 研修での作業手順、当日の段取り |
| `talk` | the following talk | 上のどれにも当てはまらない短い話 |

`intro` は必ず次の形にする。番号は本番と違って常に 1 から 3 とする（アプリが1セット3問で完結するため）。

```
Questions 1 through 3 refer to the following <言い回し>.
```

### 選定ルール

1. `data/part4/history.json` を読み、直近の `items` を確認する。
2. **直近10件に出た場面（`scene`）は選ばない。**（5本まとめて作るので、1回分＝5件を2回さかのぼる）
3. **この回の5本は、5つとも別の `talkType` にする。** 同じ種類を2本入れない。
4. 5本の枠の配分は **優先枠3本・標準枠2本**を基本とし、3回に1回ほど標準枠の1本を低頻度枠に替える。
5. 決めた場面は `scene` に「大分類｜具体的な状況」の形で書く（例 `留守番電話｜納品の遅れと代替案`）。
   `scene` はアプリでは**解き終わるまで表示されない**。先読みの練習を崩さないため。

### この回の5本を散らす

| 項目 | 5本の中での決まり |
|---|---|
| トークの種類 | 5つとも別（上記3）。優先枠3・標準枠2 |
| 場面 | 5つとも別。直近10件とも重ならない |
| 話し手 | `M` と `W` の両方を使う。どちらかに4本以上偏らせない |
| アクセント | `en-US` / `en-GB` / `en-AU` / `en-CA` から選び、同じものを3本以上使わない |
| 設問の型 | 3問の組み合わせが**全部同じ**にならないようにする。`intent` と `infer` を合わせて2本以上に入れる |
| 正解の位置 | 5本×3問＝15問で、A・B・C・D が**それぞれ2問以上**になるようにする |

### 話し手

`speaker` は**1人だけ**。`{ "tag": "M" または "W", "role": "男性" / "女性", "accent": "en-US" など }`。

- **`speakers`（複数形）は書かない。** Part 4 は1人が話すので、機械の確認で弾かれる。
- `accent` は4か国のいずれか。本番は4か国の発音を混ぜる。
  **注意：** 音声生成ではアクセントを指定できない。`accent` は端末の読み上げに落ちたときだけ効く。それでも本番の構成を記録として残すため必ず入れる。

## ステップ2：トークを書く

### 分量

| 項目 | 基準 |
|---|---|
| 文の数 | 7〜11文 |
| 総語数 | 110〜160語 |
| 1文の語数 | 8〜30語。極端に短い文は、**最後の1文を除いて**最大1つ |

本番のトークは35〜45秒で読み上げられる。160語を超えると本番より長くなる。

`lines` は**文ごと**に `{ "en": "...", "ja": "..." }` を並べる。**`tag` は書かない**（話し手は1人）。

### トークの型

Part 4 のトークは**必ず「筋のある型」**になっている。次のいずれかに当てはめる。

| 型 | 展開 |
|---|---|
| 問題と代替案 | 名乗り → 問題の発生 → 原因 → 代替案 → 依頼と期限 |
| 告知と指示 | 告知 → 理由 → 手順 → 聞き手への依頼 → 補足 |
| 変更の説明と依頼 | 主題 → 変更の中身 → 理由（現状の数字）→ 新しい手順 → 依頼と期限 |
| 経歴と紹介 | 謝辞 → 誰の何の場か → 経歴 → 功績 → これから → 締め |
| 状況と代替手段 | 名乗りと主題 → 状況 → 影響（数字）→ 代わりの手段 → 注意 → 次回の予告 |

**禁止：** 筋のない情報の羅列、結論の出ない話、聞き手への関わりが無い話。設問が作れなくなる。

### 書き方の制約

- 現実の場面として成り立つ具体性を持たせる（金額、曜日、部署名、時刻、所要時間など）。ただし固有名詞は架空のものにする。
- **語彙は TOEIC 頻出語の範囲**に収める。専門用語・スラング・略語は避ける。
- 言い換えを必ず仕込む。本番の正解選択肢は本文の語をそのまま使わない（`held up` → `delayed`、`waived` → `free`、`check a bag` → `leave a bag` など）。
- **句動詞・熟語を3つ以上入れる**（`hold up`、`run short on`、`wrap up`、`stay on` など）。易しい単語だけで書くと、語注に入れる価値のある語が残らない。
- 数字は2つ以上入れる。**現状と改善後**、**通常時と今日**のように、対になる数字を置くと設問が作りやすい。
- 聞き手への依頼（`call me back before five`、`sign up by Friday`）を必ず1つ入れる。Part 4 の3問目はここから作られることが多い。
- `ja` は1文ずつ、その文だけの自然な日本語訳にする。前後の文の情報を混ぜない。

## ステップ3：設問を3問作る

### 型の配分

`type` は次の6種から選ぶ。**1セットに同じ型を2つ入れない。**

| type | 何を問うか | 設問文の例 |
|---|---|---|
| `gist` | 全体の話題・目的 | What is the speaker mainly discussing? / Why is the speaker calling? |
| `who` | 話し手・聞き手が誰か | Who most likely is the speaker? / Who is the message intended for? |
| `detail` | 特定の事実・理由 | Why was the gate changed? / What does the speaker say about the blue line? |
| `intent` | 発言の意図 | What does the speaker mean when he says, "..."? |
| `next` | 次の行動・依頼 | What are the listeners asked to do? |
| `infer` | 明示されない推測 | What does the speaker imply about parking? |

**1問目は必ず `gist` か `who`。** 本番の Part 4 は「何の話か・誰の話か」から始まる。根拠は冒頭3文以内に置く。

**3問目は `next` / `infer` / `detail` のいずれかにする。** 本番は終盤の内容を問う形が多い。

**並び順はトークの流れと一致させる。** 根拠の先頭文が後ろへ進む形にする。1問目に終盤の内容を問うことはない。

`graphic`（図表問題）は**使わない**。アプリが図表を表示できないため。

### 選択肢

- 各設問4択。`key` は `A` `B` `C` `D`。
- 長さを揃える（3〜8語）。正解だけ長い・短いは避ける。
- **誤答は本文に出た語を使って作る。** トークに出てこない話を選択肢にすると、消去法で解けてしまう。
  - 例：別の話題に属する数字、話し手ではなく別の人がする行為、時期のずれ、多義語の別の意味
- `ja` に各選択肢の自然な日本語訳を入れる（短く）。

### 根拠

- `evidence` は `lines` の**添字（0始まり）の配列**。その設問を解くのに必要な文だけを入れる。
- 1文だけで答えが出る設問と、2文必要な設問を混ぜる。全問1文だと本番より易しい。
- `intent` の設問では、**引用した文とその直前の文**を入れる。意図は直前の文脈で決まるため。

## ステップ4：解説・語彙・Point

### explanation（設問ごとの解説・日本語）

- 2〜4文。「どの発言が根拠か」「なぜ他が違うか」を書く。
- 引用は英語のまま短く引く（`fares are being waived` など）。
- 誤答のうち**最も紛らわしいもの1つ**には必ず触れる。

### tip（設問ごとの聞き方・日本語）

- 1〜2文。**その1問の中で閉じた話**を書く（この選択肢の引っかけ方、この根拠の探し方）。
- 解説ステップで解説の下に出る。

### glossary（語注）

- **8〜12語**。トークに実在する語・熟語だけ。
- キーは**本文の表層形を小文字化したもの**（`held up`、`filed online` など。原形に直さない）。
- 値は `{ "lemma": 原形, "pos": 品詞, "ja": 訳, "note": 補足 }`。`note` は不要なら空文字。
- `pos` は時事の語彙と同じ「名／動／形／副／前／接／熟」。複数品詞は「名・動」、熟語・句動詞・コロケーションは「熟」。`n` / `v` などの英語略号は使わない。

**何を入れるか。** ここはアプリの「語彙」ステップにそのまま並ぶ。内容語を機械的に拾うと
`afternoon` `ticket` `price` のような語ばかりになり、600点台の学習者にとって読む価値が無くなる。
**覚えて初めて点が動く語だけ**を選ぶ。

**半分以上は2語以上のまとまりにする。** 単語1語で覚えても本番では効きにくく、Part 4 で差が付くのはこちらのため。

| 優先 | 何を入れるか | 例 |
|---|---|---|
| 1 | 句動詞・熟語 | `hold up`、`run short on`、`wrap up`、`stay on`、`fill up`、`sign up` |
| 2 | 言い換えペア | 本文と正解選択肢で置き換わる組（`waive` ⇔ `free`、`check a bag` ⇔ `leave a bag`）。`note` に相手側の語を書く |
| 3 | 場面ごとの定型 | `returning your call`、`now boarding`、`at no charge`、`short notice`、`raise a glass to` |
| 4 | 多義語のその場の用法 | `check`（預ける）、`hold`（貨物室）、`claim`（申請）、`file`（提出する）。**この用法を `note` に書く場合だけ**入れる |
| 5 | TOEIC 頻出の単語 | `invoice`、`reimbursement`、`successor`、`fare`、`aircraft`、`shipment` |

**入れないもの。**

- 高校初級までの単語を、その基本の意味のまま入れる（`ticket` 切符、`morning` 朝、`finish` 終える）。同じ語でも多義の用法を扱うなら可（上の4）。
- 訳を読んでも「知っていた」で終わる語。迷ったら入れない。**8語に届かないなら、トークの側に熟語や言い換えを仕込んでから作り直す。** 数合わせで易しい語を足さない。
- `the` や `and` のような機能語。

### point（セット全体の総括）

```json
"point": {
  "flow": "名乗りと用件 → 問題 → 原因 → 代替案 → 依頼と期限",
  "items": [
    { "title": "短い見出し", "body": "次のセットで再現できる手順として書く" }
  ]
}
```

- `flow` はこのトークの展開を矢印でつないだ1行。同じ型に次に出会ったとき、設問の順番まで予測できるようにする。
- `items` は2〜3項目。**設問ごとの注意ではなく、セット全体を貫く聞き方**を書く。「留守電は名乗り・用件・依頼の3点で聞く」「依頼が複数あるときは期限で選ぶ」のように、このトークの内容から離れても使える形にする。
- 設問1問だけに閉じた話は `tip` 側に書き、ここには入れない。

## ステップ5：JSON の出力

### 5-1. 出力先

| 状況 | 動作 |
|---|---|
| 実行環境にアプリのリポジトリがある | `data/part4/<id>.json` を**5本**書き出し、`index.json` と `history.json` を更新してコミット＆プッシュ |
| リポジトリが無い／書き込みに失敗した | JSON を **`json` 指定のコードブロック**でセットごとに出力し、失敗した旨も必ず報告する |

**5本は1つのコミットにまとめる。** 途中で1本が作れなくなった場合は、**できた分だけを書き出して push し、何本作れたかを報告する**。5本そろわないことを理由に全部を捨てない。

**作業は必ず `main` ブランチに対して行う。** クラウドの実行環境は既定で作業用ブランチ（`claude/...`）を切ることがあるが、**GitHub Pages が配信しているのは `main` だけ**なので、作業ブランチに置いたセットはアプリに出てこない。プルリクエストも作らない。

```bash
git checkout main
git pull --ff-only origin main
# ここで JSON を書き出す
git add data/part4
git commit -m "Part 4 追加: <日付> の5セット"
git push origin main
```

push したら `git branch --show-current` が `main` であることと、`git status` が clean であることを確認する。

**時事英語（`data/news/`）と Part 3（`data/part3/`）には触れない。** それぞれ別ルーティンで動いており、片方の失敗がもう片方に影響しないように分けている。

### 5-2. スキーマ（v1）

```json
{
  "schemaVersion": 1,
  "type": "part4",
  "id": "2026-09-20-0500-1",
  "date": "2026-09-20",
  "time": "05:00",
  "createdAt": "2026-09-20T05:00:00+09:00",
  "sample": false,
  "scene": "留守番電話｜納品の遅れと代替案",
  "talkType": "voicemail",
  "intro": "Questions 1 through 3 refer to the following telephone message.",
  "speaker": { "tag": "M", "role": "男性", "accent": "en-US" },
  "lines": [
    { "en": "...", "ja": "..." }
  ],
  "questions": [
    {
      "id": "q1",
      "type": "gist",
      "prompt": "Why is the speaker calling?",
      "choices": [
        { "key": "A", "text": "...", "ja": "..." },
        { "key": "B", "text": "...", "ja": "..." },
        { "key": "C", "text": "...", "ja": "..." },
        { "key": "D", "text": "...", "ja": "..." }
      ],
      "answer": "B",
      "evidence": [0, 1],
      "explanation": "日本語の解説",
      "tip": "この設問の聞き方"
    }
  ],
  "glossary": {
    "held up": { "lemma": "hold up", "pos": "熟", "ja": "遅れる、滞る", "note": "delay の言い換え" }
  },
  "point": {
    "flow": "...",
    "items": [{ "title": "...", "body": "..." }]
  }
}
```

**`audio` は書かない。** トーク音声は GitHub Actions（`.github/workflows/part3-audio.yml`）がこのセットを main で見つけたあとに作り、`audio` を足して別コミットで入れる。ここで書くと作り直しの判定が壊れる。前置き（`intro`）もナレーターの声で音声に入るので、別途用意する必要はない。

### 5-3. index.json の更新

`data/part4/index.json` の `items` の**先頭**に次を挿入する。`scene` は入れない（一覧で場面が見えると先読みの意味が薄れる）。

```json
{ "id": "2026-09-20-0500-1", "no": 6, "date": "2026-09-20", "time": "05:00",
  "talkType": "voicemail", "kind": "留守番電話", "questions": 3, "file": "2026-09-20-0500-1.json" }
```

- `no` は Part 4 の通し番号。**既存項目の最大値 + 1** から順に振る（無ければ 1 から）。アプリはこれを「Part 4 #6」として出す。
- `kind` は種類の日本語（留守番電話／アナウンス／会議の一部／スピーチ／広告／放送／案内／指示／トーク）。一覧の見出しになる。
- 5本ぶんを、**1本目が小さい番号**になるように先頭へ挿入する（`items` は新しい順なので、5本目・4本目…1本目の順に並ぶ）。
- `updatedAt` を JST の実時刻に更新する。**古い項目は削除しない。**

### 5-4. history.json への追記

`data/part4/history.json` を読み（無ければ作る）、`items` の**先頭**に次を挿入する。場面と種類の重複判定は次回以降ここを見るため、**この追記を忘れると判定が壊れる**。

```json
{ "id": "2026-09-20-0500-1", "date": "2026-09-20", "scene": "留守番電話｜納品の遅れと代替案",
  "genre": "留守番電話", "talkType": "voicemail", "types": ["gist", "detail", "next"], "flow": "問題と代替案" }
```

- `genre` はステップ1の表の分類名、`flow` はステップ2で選んだ型の名前。
- **古い項目は削除しない。**
- `updatedAt` を JST の実時刻に更新する。


## 注意事項

- **1回5セット。** 週1回の実行で1週間ぶんを作る。5本を超えて作らない。
- **音声のことは何もしない。** Actions が別途作る。音声がまだ無いセットは端末の読み上げで再生されるので、学習は止まらない。
- **アプリの画面仕様に合わせる。** `scene` は解き終わるまで表示されない。`intro` は設問ステップに最初から出る（本番でも必ず聞かされるため）。`speaker.role` は「男性」「女性」のような短い語にする。
- トークの内容に実在の企業名・製品名・人名を使わない。架空のものにする。
- 政治的・宗教的な主張、健康や金銭の助言になる内容は扱わない。TOEIC の出題範囲外であり、学習の妨げになる。
