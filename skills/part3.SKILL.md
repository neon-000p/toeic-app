# part3-toeic-trainer

TOEIC Part 3（3人以下の会話 + 設問3問）の練習セットを作る。**1回の実行で1セット**。通勤の片道1回で終わる量に合わせている。

出力先は学習アプリのリポジトリ `data/part3/`。アプリ（GitHub Pages 上の `part3.html`）はこの JSON だけを読む。

**本番の形式をそのまま再現することが唯一の目的**である。面白い会話や凝った設問を作ることではない。本番で起きないことは、ここでも起こしてはならない。

---

## ステップ0：日付・時刻の確定（必ず最初に実行）

日付・時刻の基準は必ず **JST（日本標準時, UTC+9）** とする。

1. 最初に必ずシェルで現在時刻を取得する。**`TZ=Asia/Tokyo date` を単独で信用しない。**
   タイムゾーン情報を持たない環境（Windows の Git Bash など）では `TZ` が黙って無視され、
   **UTC がそのまま返る**。9時間ずれた時刻で id を作ると、その日の分が前日扱いになる。
   次のどちらかで取り、結果が日本時間として妥当かを必ず目で確かめる。

   ```bash
   node -e "console.log(new Intl.DateTimeFormat('sv-SE',{timeZone:'Asia/Tokyo',dateStyle:'short',timeStyle:'short'}).format(new Date()))"
   ```

   ```bash
   date -u '+%Y-%m-%d %H:%M'   # この結果に手で +9 時間する
   ```
2. `id` はこの実時刻から `YYYY-MM-DD-HHMM` として作る（例 `2026-09-14-0530`）。
3. 実行環境が返すキャッシュ時刻（「as of ...Z」など）を現在時刻として使ってはならない。

## ステップ1：場面の決定

### 場面は3層の「重み付けローテーション」で選ぶ

**優先枠（高頻度・本番で最も出る）**

| 場面 | 中身の例 |
|---|---|
| 社内調整 | 会議の日程、会議室、備品、シフト、承認待ち |
| 顧客対応 | 受注、納期、見積、クレーム、問い合わせ |
| 出張・移動 | 宿泊、航空便、送迎、経費 |

**標準枠**

| 場面 | 中身の例 |
|---|---|
| 採用・研修 | 面接日程、研修準備、新人の受け入れ |
| 店舗・サービス | 在庫確認、配送日、修理受付、予約 |
| 設備トラブル | 機器の故障、工事、停電、システム障害 |
| 広報・販促 | 展示会、資料、Webサイト、掲載 |
| 請求・経理 | 請求書の誤り、支払期日、精算 |

**低頻度枠**

| 場面 | 中身の例 |
|---|---|
| オフィス移転 | 引っ越し日程、レイアウト、住所変更 |
| イベント運営 | 会場、受付、参加人数、ケータリング |
| 製造・在庫 | 生産遅れ、部品、検品、倉庫 |

### 選定ルール

1. `data/part3/history.json` を読み、直近の `items` を確認する。
2. **直近5回に出た場面は選ばない。**
3. 優先枠から選ぶ確率を高くする（おおよそ 優先6：標準3：低頻度1）。本番の出題比率に寄せるため。
4. 決めた場面は `scene` に「大分類｜具体的な状況」の形で書く（例 `社内｜会議室の予約変更`）。

### 話者構成

- **4回に1回だけ3人**にする。本番でも3人会話は全13セット中2〜3セット程度で、多用は本番と乖離する。
- 2人のときは `M` と `W`。3人のときは `W` + `M` + `M2`、または `M` + `W` + `W2`。同性2人を混ぜると聞き分けが本番より難しくなるため、**3人目は必ず既出と別の性別か、同性なら役割を明確に分ける**。
- `accent` は `en-US` / `en-GB` / `en-AU` / `en-CA` から話者ごとに別のものを割り当てる。本番は4か国の発音を混ぜる。
  **注意：** 音声生成ではアクセントを指定できない。`accent` は端末の読み上げに落ちたときだけ効く。それでも本番の構成を記録として残すため必ず入れる。

## ステップ2：会話を書く

### 分量

| 項目 | 基準 |
|---|---|
| 行数 | 2人なら 8〜11行、3人なら 10〜13行 |
| 総語数 | 100〜150語 |
| 1行の語数 | 8〜25語。極端に短い行（`Sure.` だけ等）は、**最後の1行を除いて**最大1つ。締めの `Thank you both.` のような行は短くてよい |

本番の会話は30〜45秒で読み上げられる。150語を超えると本番より長くなる。

### 会話の型

Part 3 の会話は**必ず「動きのある型」**になっている。次のいずれかに当てはめる。

| 型 | 展開 |
|---|---|
| 問題と解決 | 問題の発生 → 原因 → 代替案 → 可否 → 次の行動 |
| 比較と決定 | 依頼 → 2案の提示 → 条件の比較 → 決定と理由 → 次の行動 |
| 依頼と調整 | 依頼 → 制約の提示 → 妥協案 → 合意 → 分担 |
| 報告と指示 | 報告 → 確認の質問 → 判断 → 指示 → 期限 |

**禁止：** 雑談だけで終わる会話、結論が出ない会話、情報の羅列。設問が作れなくなる。

### 書き方の制約

- 現実のビジネス会話として成り立つ具体性を持たせる（金額、曜日、部署名、時刻など）。ただし固有名詞は架空のものにする。
- **語彙は TOEIC 頻出語の範囲**に収める。専門用語・スラング・略語は避ける。
- 言い換えを必ず仕込む。本番の正解選択肢は本文の語をそのまま使わない（`book` → `reserve`、`can't make it` → `unavailable` など）。
- 数字は2つ以上入れる。3人会話では**別の話者から違う数字を出す**（突き合わせの設問を作るため）。
- `ja` は1行ずつ、その行だけの自然な日本語訳にする。前後の行の情報を混ぜない。

## ステップ3：設問を3問作る

### 型の配分

`type` は次の5種から選ぶ。**1セットに同じ型を2つ入れない。**

| type | 何を問うか | 設問文の例 |
|---|---|---|
| `gist` | 全体の話題・場所・職業 | What are the speakers mainly discussing? / Where most likely are the speakers? |
| `detail` | 特定の事実・理由 | Why does the man choose the later flight? / What problem does the woman mention? |
| `intent` | 発言の意図 | What does the woman mean when she says, "..."? |
| `next` | 次の行動・依頼 | What will the man probably do next? / What does the woman ask the man to do? |
| `infer` | 明示されない推測 | What is suggested about the new office? |

**並び順は会話の流れと一致させる。** 本番は「前半の設問 → 中盤 → 終盤」の順に並ぶ。1問目に終盤の内容を問うことはない。

**推奨の組み合わせ**

- `gist` + `detail` + `next`（最も多い型）
- `detail` + `intent` + `next`
- `gist` + `detail` + `infer`

`graphic`（図表問題）は**使わない**。アプリが図表を表示できないため。

### 選択肢

- 各設問4択。`key` は `A` `B` `C` `D`。
- 長さを揃える（3〜8語）。正解だけ長い・短いは避ける。本番の選択肢は見た目で正解が分からない。
- **誤答は本文に出た語を使って作る。** 会話に出てこない話を選択肢にすると、消去法で解けてしまう。
  - 例：選ばれなかった案の特徴、別の話者がした発言、数字の入れ替え、時制のずれ
- `ja` に各選択肢の自然な日本語訳を入れる（短く）。

### 根拠

- `evidence` は `lines` の**添字（0始まり）の配列**。その設問を解くのに必要な行だけを入れる。
- 3人会話の突き合わせ設問では、**別の話者の行を2つ以上**入れる。
- 1行だけで答えが出る設問と、2行必要な設問を混ぜる。全問1行だと本番より易しい。

## ステップ4：解説・語彙・Point

### explanation（設問ごとの解説・日本語）

- 2〜4文。「どの発言が根拠か」「なぜ他が違うか」を書く。
- 引用は英語のまま短く引く（`put the savings toward the client dinner` など）。
- 誤答のうち**最も紛らわしいもの1つ**には必ず触れる。

### tip（設問ごとの聞き方・日本語）

- 1〜2文。**その1問の中で閉じた話**を書く（この選択肢の引っかけ方、この根拠の探し方）。
- 解説ステップで解説の下に出る。

### glossary（語注）

- **12〜20語**。会話に実在する語・熟語だけ。
- キーは**本文の表層形を小文字化したもの**（`booked`、`put together` など。原形に直さない）。
- 値は `{ "lemma": 原形, "pos": 品詞, "ja": 訳, "note": 補足 }`。`note` は不要なら空文字。
- TOEIC で狙われる語を優先する。`the` や `and` のような機能語は入れない。

### point（セット全体の総括）

```json
"point": {
  "flow": "問題の発生 → 原因の切り分け → 代替案 → 制約による却下 → 保留と分担",
  "items": [
    { "title": "短い見出し", "body": "次のセットで再現できる手順として書く" }
  ]
}
```

- `flow` はこの会話の展開を矢印でつないだ1行。同じ型に次に出会ったとき、設問の順番まで予測できるようにする。
- `items` は2〜3項目。**設問ごとの注意ではなく、セット全体を貫く聞き方**を書く。「2案が出たら聞くべき3点が決まる」「3人会話には突き合わせの設問が入る」のように、この会話の内容から離れても使える形にする。
- 設問1問だけに閉じた話は `tip` 側に書き、ここには入れない。

## ステップ5：JSON の出力

### 5-1. 出力先

| 状況 | 動作 |
|---|---|
| 実行環境にアプリのリポジトリがある | `data/part3/<id>.json` に書き出し、`index.json` と `history.json` を更新してコミット＆プッシュ |
| リポジトリが無い／書き込みに失敗した | JSON を **`json` 指定のコードブロック1つ**でチャットに出力し、失敗した旨も必ず報告する |

**作業は必ず `main` ブランチに対して行う。** クラウドの実行環境は既定で作業用ブランチ（`claude/...`）を切ることがあるが、**GitHub Pages が配信しているのは `main` だけ**なので、作業ブランチに置いたセットはアプリに出てこない。プルリクエストも作らない。

```bash
git checkout main
git pull --ff-only origin main
# ここで JSON を書き出す
git add data/part3
git commit -m "Part 3 追加: <id> <場面>"
git push origin main
```

push したら `git branch --show-current` が `main` であることと、`git status` が clean であることを確認する。

**時事英語（`data/news/`）には触れない。** 別ルーティンで動いており、片方の失敗がもう片方に影響しないように分けている。

### 5-2. スキーマ（v1）

```json
{
  "schemaVersion": 1,
  "type": "part3",
  "id": "2026-09-14-0530",
  "date": "2026-09-14",
  "time": "05:30",
  "scene": "社内｜会議室の予約変更",
  "speakers": [
    { "tag": "W", "role": "女性", "accent": "en-US" },
    { "tag": "M", "role": "男性", "accent": "en-GB" }
  ],
  "lines": [
    { "tag": "W", "en": "...", "ja": "..." }
  ],
  "questions": [
    {
      "id": "q1",
      "type": "gist",
      "prompt": "What are the speakers mainly discussing?",
      "choices": [
        { "key": "A", "text": "...", "ja": "..." },
        { "key": "B", "text": "...", "ja": "..." },
        { "key": "C", "text": "...", "ja": "..." },
        { "key": "D", "text": "...", "ja": "..." }
      ],
      "answer": "B",
      "evidence": [0, 1],
      "explanation": "日本語の解説",
      "tip": "この設問の聞き方"
    }
  ],
  "glossary": {
    "booked": { "lemma": "book", "pos": "v", "ja": "予約する", "note": "" }
  },
  "point": {
    "flow": "...",
    "items": [{ "title": "...", "body": "..." }]
  }
}
```

**`audio` は書かない。** 会話音声は GitHub Actions（`.github/workflows/part3-audio.yml`）がこのセットを main で見つけたあとに作り、`audio` を足して別コミットで入れる。ここで書くと作り直しの判定が壊れる。

### 5-3. index.json の更新

`data/part3/index.json` の `items` の**先頭**に次を挿入する。`scene` は入れない（一覧で場面が見えると先読みの意味が薄れる）。

```json
{ "id": "2026-09-14-0530", "date": "2026-09-14", "time": "05:30", "speakers": 2, "file": "2026-09-14-0530.json" }
```

`updatedAt` を JST の実時刻に更新する。**古い項目は削除しない。**

### 5-4. history.json への追記

`data/part3/history.json` を読み（無ければ作る）、`items` の**先頭**に次を挿入する。場面と設問型の重複判定は次回以降ここを見るため、**この追記を忘れると判定が壊れる**。

```json
{ "id": "2026-09-14-0530", "date": "2026-09-14", "scene": "社内｜会議室の予約変更", "genre": "社内調整", "speakers": 2, "types": ["gist", "detail", "next"], "flow": "依頼と調整" }
```

- `genre` はステップ1の表の場面名をそのまま入れる。
- `flow` はステップ2で選んだ型の名前。
- **古い項目は削除しない。**
- `updatedAt` を JST の実時刻に更新する。

初回だけ、ファイル全体はこの形にする。

```json
{ "schemaVersion": 1, "type": "part3-history", "updatedAt": "2026-09-14T05:32:00+09:00", "items": [] }
```

### 5-5. 出力前の自己検証

書き出す前に、JSON として妥当であることと以下を確認する。**壊れた JSON を置くとそのセットがアプリで開けない。**

- `lines` が範囲内の行数（2人 8〜11行 / 3人 10〜13行）で、総語数が 100〜150語
- すべての `lines[].tag` が `speakers[].tag` のいずれかと一致する
- すべての `lines` に `en` と `ja` が揃っている
- `questions` が3問、`type` が重複していない、`graphic` を使っていない
- 各設問4択で、`answer` が `choices` の `key` のいずれかと一致する
- すべての選択肢に `ja` がある
- すべての `evidence` が `lines` の実在する添字（0 以上 `lines.length - 1` 以下）
- 設問の並びが会話の流れと一致している
- `glossary` が12〜20語で、全キーが会話本文に実在する小文字表層形である
- `point.items` が2〜3項目で、設問1問に閉じた話になっていない
- `audio` を書いていない
- `index.json` と `history.json` の先頭に今回の項目を追記した
- 3人会話の回なら、`evidence` に別の話者の行を2つ以上含む設問が1問以上ある

## 注意事項

- **1回1セット。** まとめて複数セットを作らない。1回分の量を超えると通勤の片道で終わらない。
- **音声のことは何もしない。** Actions が別途作る。音声がまだ無いセットは端末の読み上げで再生されるので、学習は止まらない。
- **アプリの画面仕様に合わせる。** `scene` は解き終わるまで表示されない。`speakers[].role` は「男性」「女性」のような短い語にする。
- 会話の内容に実在の企業名・製品名・人名を使わない。架空のものにする。
- 政治的・宗教的な主張、健康や金銭の助言になる内容は扱わない。TOEIC の出題範囲外であり、学習の妨げになる。
